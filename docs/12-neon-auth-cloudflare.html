Authentification réelle : Neon Auth + Cloudflare Workers

Cette note définit le lot d’identité sans absorber l’adaptateur PostgreSQL, l’identité service ou le déploiement Cloudflare.

Contexte et objectif

Le runtime sélectionnait une identité synthétique par cookie et l’écran public ne transmettait rien. L’objectif est une inscription, une connexion, une session vérifiée et une déconnexion réelles, tout en conservant PostgreSQL comme seule autorité pour les capacités métier.

Architecture retenue

  1. Le navigateur poste les identifiants à une Server Action Next.js.
  2. Le SDK officiel relaie vers Neon Auth et pose des cookies httpOnly, secure en environnement HTTPS et SameSite=Lax.
  3. Chaque requête serveur récupère la session vérifiée et un JWT court via auth.token().
  4. Le JWT est transmis uniquement au repository membre Data API/PostgREST. La projection vers app.members et la lecture des capacités passent par une RPC métier sous RLS.
  5. Les rôles contributor/reviewer/admin restent dans app.member_role_assignments. Le formulaire, Neon Auth user.role et le client ne peuvent pas les choisir.
  6. L’identité service reste un contrat runtime distinct possédé par Queue/outbox; aucun JWT utilisateur ne lui est transmis.

Non-objectifs

  • Aucun fournisseur alternatif, OAuth social, domaine personnalisé ou plan payant.
  • Aucun rôle métier attribué automatiquement à l’inscription.
  • Aucun déploiement production avant intégration du lot runtime et preuve RLS/session.
  • Les identités synthétiques restent seulement dans les scripts de vérification hors runtime.

Configuration

  • NEON_AUTH_BASE_URL : URL publique propre à la branche Neon.
  • NEON_AUTH_COOKIE_SECRET : secret serveur stable d’au moins 32 caractères, stocké par Wrangler, jamais committé.
  • NEON_DATA_API_URL : endpoint PostgREST propre à la branche; le JWT Neon Auth est attaché côté serveur aux lectures et RPC membre.
  • OUTBOX_DATABASE : Hyperdrive distinct possédé par Queue/outbox.
  • TRUSTED_DATABASE_URL : secret de connexion de la continuation fingerprint. Aucun JWT utilisateur n’est transmis à ces deux identités service.

Acceptation

  • TypeScript strict, contrats runtime et build Next réussissent localement.
  • Une route proxy Auth dynamique, l’inscription/connexion, la session et le logout existent.
  • Aucun rôle métier n’est accepté depuis le client.
  • Les preuves development JWT → RPC, cohérence d’identité A/B et témoin RLS métier sont acquises après l’intégration du runtime Data API.
  • À prouver avant toute preview ou production : cycle applicatif déployé avec cookies HTTPS, getSession(), token(), logout et absence de secret dans les logs/builds.
  • La migration 0007 définit deux projections catalogue anonymes en lecture seule. Leur application et leurs témoins positif/négatif sur Neon development restent requis avant une nouvelle preview ; aucune RPC membre ou table directe ne devient anonyme.

Ressource existante

Projet Neon idea-commons, branche development, région aws-eu-central-1. Neon Auth et la Data API étaient déjà actifs; ce lot n’a créé aucune ressource distante supplémentaire. La Data API development est https://ep-square-breeze-a2ftwoml.apirest.eu-central-1.aws.neon.tech/neondb/rest/v1.
