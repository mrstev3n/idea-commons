Spécification d'exécution · M0

Une migration rejouable, un refus par défaut prouvé.

Ce document fixe le résultat attendu avant l'écriture du SQL M0. Il transforme le contrat validé dans docs/05-data-model-rls.html en livrables, contrôles et critères observables, sans toucher à Neon production.

1. Contexte, objectif et non-objectifs

Contexte

IC-01 à IC-05 sont validés. Le modèle public définit une base PostgreSQL unique, des schémas séparés, Neon Auth comme identité et une seconde barrière RLS. Aucun objet métier n'est encore appliqué à un environnement distant.

Objectif

Livrer une première migration PostgreSQL versionnée et un harnais de tests multi-identités qui prouvent les invariants locaux, les privilèges minimaux et l'isolation des données privées.

Non-objectifs

Variantes régionales, contributions détaillées, IA, paiements, clés fournisseurs, invitations dans l'interface, recherche externe, stockage R2 effectif, activation de la Data API et promotion vers production.

Résultat attendu

Une base vide accepte la migration une fois, refuse son rejeu accidentel, expose uniquement les opérations prévues aux rôles Data API et produit les résultats RLS attendus avec des données entièrement synthétiques.

2. Principes d'implémentation

  • Refus par défaut : aucun droit implicite de PUBLIC, aucune politique globale permissive et aucun rôle applicatif avec BYPASSRLS.
  • Défense en profondeur : contraintes relationnelles, privilèges d'objet, politiques séparées par opération et fonctions étroites à search_path fixé.
  • Identité unique : les tables métier ne copient ni email, ni mot de passe, ni session ; elles référencent l'UUID externe par app.members.auth_user_id.
  • État public immuable : une version publiée ne peut plus être modifiée ou supprimée ; le pointeur courant ne cible qu'une version publiée de la même idée.
  • Portabilité : SQL PostgreSQL lisible sans ORM, migration transactionnelle et shim d'identité limité aux tests locaux.
  • Budget : aucune dépendance payante ni ressource distante supplémentaire n'est requise pour produire le livrable.

Portée de la preuve : RLS prouve la visibilité des lignes et les mutations autorisées en base. Les réponses HTTP normatives 401, 403 et 404, les en-têtes de cache et les URLs signées seront prouvés au niveau applicatif lorsqu'une API existera.

5. Critères d'acceptation observables

  1. Chaque table possède une clé primaire, un propriétaire de donnée explicite, une visibilité documentée et les index de ses clés étrangères ou prédicats RLS.
  2. RLS est activée sur chaque table de chemin utilisateur ; les rôles de trafic ne possèdent pas les tables, restent NOBYPASSRLS et aucun accès privé ne dépend seulement d'une vue ou de l'application.
  3. Les rôles Data API reçoivent uniquement USAGE sur app et les opérations nécessaires ; app_private reste inaccessible.
  4. Une version publiée exige date, licence, contenu objet et sources pour chacun de ses claims factuels ; elle devient immuable.
  5. Un projet référence durablement une version source publiée et conserve son propriétaire ; les writes concurrents passent par une révision attendue.
  6. Les six identités de test produisent les lectures et refus attendus avec uniquement des UUID, textes et fichiers fictifs.
  7. Le contrôle des clés étrangères ne signale aucun index manquant ; le catalogue des politiques ne signale aucune table utilisateur sans RLS forcée.
  8. Le diff public ne contient ni secret, ni donnée personnelle réelle, ni fichier de travail local, ni configuration interne.

6. Séquence distante et limites

Aucune action distante dans ce livrable. Après audit du SQL et succès local, une validation distincte pourra appliquer la migration à la branche Neon development. La Data API restera désactivée jusqu'à vérification des rôles, révocations, privilèges et politiques. Neon production exige une décision humaine ultérieure et séparée.

Le harnais local émule seulement auth.user_id() afin de tester les politiques PostgreSQL. Il ne prétend pas valider la signature d'un JWT, le proxy Data API, Neon Auth, le comportement HTTP de l'application ni une approbation humaine.
