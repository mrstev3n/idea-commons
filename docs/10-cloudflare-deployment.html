Surface Cloudflare du prototype Next.js

Cette spécification sépare la cible d'hébergement de l'état réellement déployable du prototype IC-07.

Décision

Cible : Cloudflare Workers avec vinext, désormais recommandé par Cloudflare pour une nouvelle application Next.js 16. Pages classique est exclu : il ne convient qu'à un export statique, alors qu'Idea Commons comporte SSR, Server Actions et Route Handlers.

État : configuration locale prête à être revue, mais déploiement bloqué. Le build Workers réussit ; le runtime dynamique échoue tant que les adaptateurs PGlite, filesystem local et processus enfant restent actifs.

Périmètre et non-objectifs

  • Configurer le packaging Workers, les previews et les commandes de publication.
  • Ne pas modifier l'authentification, créer de ressource distante, ajouter de secret ou déployer.
  • Ne pas présenter les pages publiques qui répondent localement comme une application complète prête à exposer.

Les previews Workers sont publiques par défaut. Les flux éditoriaux ne doivent pas être exposés avant l'authentification cible ; Cloudflare Access est une option de protection séparée, pas activée implicitement.

Bloqueurs avant publication

  1. Remplacer PGlite par l'adaptateur Neon/PostgreSQL cible ; le VFS Workers n'offre qu'un /tmp mémoire, isolé et non persistant par requête.
  2. Remplacer le pont node:child_process par un appel d'adaptateur dans le runtime ; le module Workers est un stub non fonctionnel.
  3. Sortir la consommation de l'outbox du GET de polling vers un consommateur durable borné.
  4. Valider ensuite l'identité service, l'authentification et les secrets dans des environnements séparés.

npm run cloudflare:preflight bloque les commandes de preview et de production tant que ces marqueurs sont présents.

Preuves d'acceptation

  • npm run typecheck et npm run build restent verts.
  • npm run build:vinext construit le Worker sans erreur.
  • Le runtime Workers local rend les routes publiques et dynamiques attendues sans 500.
  • Le préflight ne passe qu'après remplacement réel des trois adaptateurs bloquants.
  • Après autorisation : dev obtient un alias stable observé, puis main une URL de production observée.

Coûts et limites

La configuration n'active ni KV, ni Images, ni service payant. Elle vise le plan Workers Free, mais le SSR et les traitements lourds peuvent dépasser sa limite CPU ; tout passage au plan Workers Paid, actuellement annoncé à partir de 5 USD par mois, exige une décision humaine séparée. Les plafonds et tarifs doivent être revérifiés au jalon de déploiement.
