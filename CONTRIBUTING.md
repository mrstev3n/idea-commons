# Contribuer à Idea Commons

Merci de vouloir améliorer Idea Commons. Les contributions peuvent porter sur le code, la documentation, les idées publiques, les preuves, les traductions ou les adaptations locales.

## Avant de contribuer

1. Vérifiez que le changement respecte la mission et les principes du [cadrage produit](docs/product-concept.html).
2. Pour un changement important, ouvrez d'abord une discussion ou une issue décrivant le problème, la portée et les alternatives.
3. N'incluez jamais de secret, donnée personnelle, projet privé ou contenu tiers sans droits suffisants.
4. Distinguez clairement faits sourcés, hypothèses, estimations, recommandations et questions à valider.

## Licences des contributions

En soumettant une contribution, vous acceptez qu'elle soit distribuée sous la licence applicable à la zone modifiée :

- code logiciel : `AGPL-3.0-only`, voir [LICENSE](LICENSE) ;
- contenu éditorial public : `CC BY-SA 4.0`, voir [CONTENT-LICENSE.md](CONTENT-LICENSE.md) ;
- éléments tiers : leur licence propre, qui doit être identifiée et compatible.

Les contributions suivent le principe « licence entrante = licence sortante ». Aucun transfert général de droits d'auteur au mainteneur n'est demandé.

## Developer Certificate of Origin

Chaque commit contributif doit être signé avec un trailer `Signed-off-by`, par exemple :

```bash
git commit -s -m "docs: clarify contribution evidence"
```

Ce sign-off certifie le [Developer Certificate of Origin 1.1](https://developercertificate.org/) : vous avez le droit de soumettre la contribution sous la licence indiquée et vous comprenez que la contribution et son historique sont publics et conservés.

N'utilisez pas de trailer `Co-authored-by`. Lorsqu'un travail possède plusieurs auteurs, chacun doit contribuer ou certifier sa propre part d'une manière traçable et compatible avec le DCO.

## Contenu, traductions et adaptations

- Une affirmation présentée comme un fait doit référencer une source vérifiable.
- Une traduction ou adaptation doit identifier la version source et décrire les changements importants.
- Une adaptation régionale ne doit pas écraser silencieusement l'idée source.
- Une contribution issue d'un projet privé doit être recréée comme proposition publique distincte, sans donnée confidentielle.
- Les citations restent limitées et attribuées ; ne copiez pas un contenu propriétaire pour le « reformuler ».

## Proposition et revue

1. Créez une branche courte depuis la branche cible indiquée par le projet.
2. Réalisez un lot cohérent et limité.
3. Exécutez les contrôles pertinents et documentez leurs résultats.
4. Ouvrez une pull request expliquant le problème, le changement, les zones affectées, les preuves et les limites.
5. Répondez aux retours sans masquer les désaccords ou vérifications manquantes.

Une contribution peut être corrigée, refusée, dépubliée ou archivée pour des raisons de qualité, preuve, sécurité, droits, portée ou conduite. Un refus n'implique pas un jugement sur la personne qui contribue.

## Acceptation

Une contribution est intégrée seulement lorsqu'un mainteneur autorisé estime qu'elle respecte les licences, la portée, les preuves attendues et la direction du projet. Une vérification automatisée ne constitue pas une approbation humaine.

Les rôles et le processus de décision sont décrits dans [GOVERNANCE.md](GOVERNANCE.md). Toute participation est soumise au [Code de conduite](CODE_OF_CONDUCT.md).
